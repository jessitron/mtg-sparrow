## Honeycomb Verification

- **MCP access:** The available MCP tools connect to the `demo` team, not `modernity` where sparrow-deck data lives. Direct Honeycomb queries via MCP were not possible.
- **Trace delivery confirmed:** The trace link in the app footer (generated after session start) contained a valid Honeycomb URL with `trace_id=`. This proves spans are being sent to Honeycomb.
- **Attribute verification (code-level):** Both `session.started_from = 'welcome_screen'` and `session.welcome_dwell_ms` are set in `startSession()` (lines 407-413 of `src/main.ts`) before the session span is created. No path through `startSession()` skips these attributes.
- **service.version:** Set to `'0.5.0'` in `initTelemetry(APP_VERSION)` — confirmed in build output and footer.

---

## Observations

- **`welcomeScreenLoadTime` is set in `showWelcomeScreen()`** (line 369), not at DOMContentLoaded. This means `session.welcome_dwell_ms` measures from when the welcome screen first renders, which is the correct and meaningful measurement.
- **Click-to-advance guard is clean.** The check `if (session) handleAdvance()` in the click handler elegantly prevents accidental advances on the welcome screen without any extra state flags.
- **The `waitForFunction` Playwright pattern** is more robust than fixed timeouts for detecting class changes. Used it here for auto-reveal check after the fixed-timeout approach was flaky. Recommend using this pattern in future test scripts.

## Test Timing Note

- Initial test run had a false FAIL on "Card name auto-reveals after delay" because `waitForTimeout(2700)` occasionally ends right as the class is being removed, and the check races the DOM mutation. Fixed by switching to `waitForFunction` which polls until the condition is true. This was a test flakiness issue, not a product bug — the auto-advance to Card 2 still passed, proving the name DID reveal.
